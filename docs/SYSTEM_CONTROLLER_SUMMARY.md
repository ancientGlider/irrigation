# Резюме: Архитектура главного контроллера системы

## Анализ текущей ситуации

После анализа модуля отображения и всей системы выявлено:

1. **Модуль `display`** содержит структуру `MainScreenState`, которая агрегирует данные из разных модулей
2. **Документация** описывает `MainScreenStateProvider` как агрегатор, но он не реализован
3. **В `loop()`** должны вызываться все FSM контроллеры последовательно
4. **Риск дублирования данных**: если каждый модуль будет читать данные напрямую, произойдёт дублирование вызовов и данных

## Предложенное решение

### Главный контроллер `SystemController`

Создан модуль `src/irrigation/system_controller`, который:

1. **Централизует управление FSM**:
   - Вызывает все FSM контроллеры в `process()`
   - Управляет порядком вызовов
   - Обеспечивает единую точку входа

2. **Агрегирует состояние системы**:
   - Хранит структуру `SystemState` с данными всех модулей
   - Обновляет состояние один раз за цикл
   - Избегает дублирования данных

3. **Преобразует состояния для дисплея**:
   - Маппинг `WateringState` → `WateringViewState`
   - Маппинг `GrowingPeriod` → `SeasonLabel`
   - Формирование `MainScreenAlerts` и `MainScreenTelemetry`

4. **Предоставляет единый API**:
   - `getDisplayState()` — готовое состояние для дисплея
   - `getSystemState()` — сырое состояние для отладки
   - Команды управления (делегируются модулям)

### Структура данных

**`SystemState`** (в `system_state.h`):
- Состояние полива (state, pump, timer)
- Состояние цикла (period, day, hour, minute)
- Состояние освещения
- Данные датчиков (soil, air temp/humidity)
- Системный режим

**`MainScreenState`** (в `display/main_screen.h`):
- Только данные, необходимые для отображения
- Преобразованные представления состояний
- Не содержит данных, не используемых дисплеем

## Преимущества архитектуры

1. ✅ **Единый источник истины**: все данные в `SystemController`
2. ✅ **Отсутствие дублирования**: данные читаются один раз за цикл
3. ✅ **Чистое разделение ответственности**:
   - `SystemController` — агрегация и оркестрация
   - `Display::MainScreen` — только отрисовка
   - Модули системы — только своя логика
4. ✅ **Оптимизация ресурсов**: минимум вызовов геттеров
5. ✅ **Легкое тестирование**: можно мокировать `SystemState`

## Интеграция в `loop()`

```cpp
void loop() {
    // Обработка всех FSM и агрегация состояния
    Irrigation::SystemController::process();
    
    // Обновление дисплея
    if (displayRefreshTimer.isReady()) {
        Display::MainScreenState state = 
            Irrigation::SystemController::getDisplayState();
        Display::MainScreen::setState(state);
        Display::MainScreen::update();
    }
}
```

## Замечания

1. **`sensorCountdown`**: В текущей реализации используется `wateringRemainingSeconds` как приближение. Возможно, потребуется отдельный таймер для отсчёта времени до следующей проверки датчиков (из настроек `SensorCheckPeriodSec`).

2. **Управление памятью**: Датчики создаются через `new` в `begin()`. Для Arduino это приемлемо, так как объекты живут всё время работы системы. Альтернатива — статические объекты, но это усложнит инициализацию.

3. **Обработка ошибок**: В текущей реализации ошибки датчиков обрабатываются через флаг `sensorsValid`. При необходимости можно добавить более детальную обработку.

## Рекомендации

1. **Модуль `display`** должен получать только `MainScreenState` из `SystemController`
2. **Модуль `display`** не должен обращаться напрямую к модулям системы
3. **Все команды управления** (ручной полив, очистка и т.д.) должны проходить через `SystemController`
4. **Тестирование** можно проводить с мокированием `SystemState`
