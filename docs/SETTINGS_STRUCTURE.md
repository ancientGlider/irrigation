# Структура настроек (Этап 4.1)

Документ описывает структуру данных, сохраняемую в EEPROM, значения по умолчанию и схему проверки целостности. Фактическая логика загрузки/сохранения будет реализована на этапе 4.2.

## 1. Структура `Settings::Data`

## 2. Заголовок и полный блок

Для управления версиями используются дополнительные структуры:

```cpp
struct Header {
    char signature[2];  // 'I', 'R'
    uint8_t version;    // 4
    uint8_t length;     // sizeof(Data)
};

struct Block {
    Header header;
    Data data;
    uint16_t crc;       // CRC16/IBM для header + data
};
```

- **Сигнатура** (`'I','R'`) позволяет быстро определить, что в EEPROM лежит блок настроек проекта.
- **Версия** используется для миграции при изменении структуры (увеличивается при любых несовместимых правках).
- **Length** — дополнительная защита от повреждённых данных и инструмент для конвертации между версиями.

Полный размер блока (`sizeof(Block)`) — 38 байт. Сигнатура и версия помогают распознать корректный блок, CRC защищает от повреждения.

## 3. Проверка целостности

- Полином: CRC16/IBM (0xA001, отражённый алгоритм)
- Диапазон: вычисляется для всех байтов `header` и `data` (CRC рассчитывается после заполнения этих полей).
- Хранение: 16-битное значение добавляется в конец блока (младший байт, затем старший).
- При чтении блок считается валидным, если:
  1. Совпадает сигнатура
  2. Совпадает номер версии
  3. `length` == `sizeof(Data)` (для текущей версии)
  4. CRC совпадает с вычисленным значением

В случае несоответствия будет использован блок по умолчанию (`Settings::DEFAULT_BLOCK`).

## 4. Валидация значений

- При чтении блока из EEPROM каждое поле проверяется по своему набору правил (диапазоны, взаимные ограничения). Если хотя бы одно значение некорректно, весь блок заменяется `DEFAULT_DATA`, а валидный блок сразу записывается обратно.
- В процессе работы `Manager::set()` повторяет те же проверки перед записью, поэтому в EEPROM никогда не попадают конфликтующие комбинации (например, `trainingMoisturePercent >= soilMoistureStartPercent` или суммарный полив > 23 часов).
- Значение `Key::CycleLengthDays` не хранится отдельно и вычисляется как сумма `germination + spring + summer + autumn`.
- Значение `Key::SystemMode` хранится напрямую и должно соответствовать перечислению `Settings::SystemMode`.

## 5. Значения по умолчанию

См. `Settings::DEFAULT_DATA` в `settings_data.h`. Они синхронизированы с описанием в `PROJECT.md` и исходным проектом `irr_ver0.2.1.2`.

- Режим системы: `SystemMode::Growing` (0)
- Калибровка датчика почвы: `500` (сухо) / `180` (влажно)
- Периоды проращивания/весны/лета/осени: `3 / 33 / 34 / 0` дней. Суммарная длительность `проращивание + весна + лето + осень` должна быть в диапазоне 30–200 дней.
- Полив: `18` секунд, пауза `600` секунд, максимум `6` повторов. Общая длительность цикла полива `(duration * attempts + pause * (attempts - 1))` должна быть <= 23 часов (82 800 секунд)
- Очистка: длительность `15` секунд, пауза `60` секунд, `10` повторов
- Проверка датчиков: `600` секунд (10 минут)

## 6. Расширение структуры

- Для добавления новых полей увеличить `STORAGE_VERSION` и зарезервировать обработку в будущем коде миграции.
- Поле `flags` зарезервировано под будущие опции без изменения версии.
- При изменении размеров обязательно обновить тесты и комментарии в данном документе.
